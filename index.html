Administrer — Niveau 1 : Assister l'administrateur du réseau

Comprendre et appliquer les lois d'Ohm et de Kirchhoff, les notions de tension, courant, résistance et puissance — indispensables pour intervenir physiquement sur des équipements actifs ou passifs d'infrastructure réseau.

Ce que j'ai fait

J'ai réalisé des travaux pratiques sur un circuit RC (R=39kΩ, C=1nF) afin d'analyser le comportement d'un filtre passe-bas. J'ai effectué des mesures de tension et de phase à différentes fréquences à l'aide d'un oscilloscope, puis tracé le diagramme de Bode correspondant.

Pourquoi je l'ai fait

Ces lois sont la base de tout équipement électronique réseau. Comprendre comment le courant et la tension se comportent dans un circuit passif est indispensable pour diagnostiquer une panne matérielle ou câbler correctement une baie réseau.

Comment je l'ai fait

Utilisation d'un oscilloscope numérique pour observer les signaux d'entrée et de sortie, mesure du déphasage entre les deux canaux, calcul de la fréquence de coupure théorique (Fc ≈ 4,08 kHz) et comparaison avec les mesures expérimentales.

Mes difficultés

La lecture précise du déphasage sur l'oscilloscope était délicate, surtout aux fréquences proches de la coupure où les signaux sont très atténués. J'ai dû recommencer plusieurs mesures pour obtenir des résultats cohérents avec le modèle théorique.

Ce que j'ai appris

J'ai compris concrètement la notion de fréquence de coupure et l'impact de chaque composant sur le comportement du filtre. J'ai aussi appris à utiliser un oscilloscope en mode double-trace et à interpréter un diagramme de Bode réel face au modèle théorique.

Connecter — Niveau 1 : Découvrir les transmissions et la ToIP

Ce que j'ai appris

Ce que j'ai fait

Pourquoi je l'ai fait

Comment je l'ai fait

Calcul analytique de la fonction de transfert H(f), tracé du diagramme de Bode asymptotique puis réel, mesures en TP pour valider le modèle. Utilisation de la relation Fc = 1/(2πRC) pour relier les composants au comportement fréquentiel.

Mes difficultés

Identifier les besoins de stockage (fichiers plats, bases de données), choisir une solution adaptée et justifier techniquement ce choix.

Ce que j'ai fait

Pour mon projet SAE FitTracker, j'ai choisi et mis en place une base de données relationnelle PostgreSQL pour stocker les utilisateurs, leurs séances d'entraînement et leurs repas. J'ai conçu le schéma de base de données (tables, clés primaires/étrangères) et écrit les requêtes SQL nécessaires.

Pourquoi je l'ai fait

Chaque application a des besoins de stockage différents. Choisir un fichier CSV, une base SQL ou une base NoSQL n'est pas anodin : cela impacte les performances, la scalabilité et la maintenabilité. Savoir argumenter ce choix est une compétence attendue dès le niveau technicien.

Comment je l'ai fait

Analyse des besoins (données structurées, relations entre entités, requêtes complexes) → choix de PostgreSQL (SGBD relationnel robuste, open source). Modélisation UML (diagramme entité-relation), création des tables en SQL, intégration avec Flask via SQLAlchemy (ORM).

Mes difficultés

La configuration de PostgreSQL dans Docker et la connexion depuis Flask ont été laborieuses (variables d'environnement, chaîne de connexion, migrations de schéma). La conception du schéma relationnel, notamment les cardinalités entre tables, demandait aussi de bien réfléchir en amont.

Ce que j'ai appris

Je maîtrise les bases du SQL (SELECT, INSERT, JOIN, WHERE) et comprends les principes de normalisation d'une base de données. J'ai aussi appris à utiliser un ORM (SQLAlchemy) qui simplifie l'interaction entre Python et la base de données tout en préservant la sécurité (protection contre les injections SQL).

Utiliser Git pour versionner son code, travailler en équipe sur un dépôt partagé, et respecter les bonnes pratiques de collaboration (commits, branches, merge requests).

Ce que j'ai fait

J'ai utilisé Git et GitHub pour versionner l'ensemble de mes projets, dont ce portfolio hébergé sur GitHub Pages. J'ai travaillé avec des branches pour isoler les développements en cours, rédigé des messages de commit descriptifs et géré les conflits lors de fusions de branches.

Pourquoi je l'ai fait

Git est l'outil de versioning standard dans toutes les équipes de développement. Sans Git, travailler à plusieurs sur le même code est chaotique et le risque de perdre du travail est élevé. C'est aussi un outil indispensable pour montrer son travail à un recruteur via GitHub.

Comment je l'ai fait

Utilisation des commandes Git de base (init, add, commit, push, pull, branch, merge) en ligne de commande, création de dépôts GitHub, configuration des GitHub Pages pour le déploiement automatique du portfolio.

Mes difficultés

Les conflits de merge lors de fusions de branches étaient déstabilisants au début : comprendre ce que Git attendait de moi et comment résoudre le conflit manuellement sans casser le code existant a demandé plusieurs tentatives et lectures de documentation.

Ce que j'ai appris

Je maîtrise le workflow Git standard (feature branch → commit → push → merge) et comprends pourquoi chaque étape est importante. J'ai aussi compris la valeur d'un historique Git propre : des commits atomiques et bien décrits permettent de comprendre l'évolution d'un projet et de revenir en arrière en cas de problème.
